# 프로토타입 비교 (prototype)

기능 하나를 **진짜로 서로 다른 방법 N개**로 만들어 나란히 비교하고, 가장 좋은 걸 골라 실제로 반영하는 스킬이에요.
사용자는 비개발자 기획자일 수 있어요. 전문용어 대신 쉬운 말로, 단계마다 지금 뭘 하는지 짧게 알려주세요.

## 입력

- **기능 설명** (필수): 예) "오늘의 코디를 바꿔보는 화면"
- **N** (선택, 기본 5): 만들 방법의 개수. 인자 끝에 숫자가 있으면 그걸 N으로 써요. 2 미만이면 2, 8 초과면 8로 맞추고 그렇게 했다고 알려줘요.
- 기능 설명이 비어 있으면 무엇을 만들지 한 번만 물어봐요.

## 진행 순서

### 0. 맥락 파악 (짧게)
- 이 기능이 들어갈 실제 파일과 기존 스타일(색·글꼴·간격·말투, 데이터 구조)을 먼저 읽어요.
- `CLAUDE.md` 의 디자인 규칙(예: 디자인 시스템 지정)이 있으면 따라요. 단, 사용자가 이번 요청에서 다른 레퍼런스를 명시하면 그걸 우선해요.
- 필요하면 **온라인으로 자유롭게 리서치**해요. (비슷한 서비스의 UI 패턴, 라이브러리, 접근성 기준 등) 쓴 출처는 마지막에 링크로 남겨요.
  - 외부 API·서비스를 쓰는 안이라면 **지금도 운영 중인지, 무료인지, 약관상 허용되는지**를 반드시 확인한 뒤에 안으로 넣어요. 기억만으로 추천하지 않아요.

### 1. 서로 다른 방법 N개 떠올리기
- **한 아이디어의 변형(색만 다름, 배치만 조금 다름)이면 안 돼요.** 상호작용 방식·정보 구조·핵심 메타포 중 적어도 하나가 근본적으로 달라야 해요.
  - 예) 코디 바꾸기: ① 영역별 좌우 캐러셀 ② 카드 스와이프(좋아요/넘기기) ③ 드래그해서 판에 올리기 ④ 슬롯머신처럼 한 번에 섞기 ⑤ 질문 3개로 좁혀가기
- 각 안마다 한 줄 요약 + "이 안이 잘 맞는 사용자/상황"을 적어요.
- 서로 겹치는 안이 있으면 버리고 새로 떠올려요.

### 2. 동작하는 preview를 HTML 파일 하나에 담기
- 파일: `prototypes/<기능-slug>.html` (폴더가 없으면 만들어요). 외부 의존성 없이 **이 파일 하나만 열면** 다 동작해야 해요.
- 상단에 탭이나 버튼으로 안 1~N을 전환하거나, 넓은 화면에서는 **나란히(그리드)** 보이게 해요. 각 preview는 휴대폰 크기(약 390px 폭) 프레임 안에 넣어요.
- 각 안 위에 이름·한 줄 설명·장단점을 붙여요.
- 가짜 데이터라도 **실제로 눌러지고 바뀌어야** 해요. 그림만 있는 목업은 안 돼요.
- 기존 서비스의 데이터·문구·스타일 토큰을 최대한 재사용해서 실제 화면과 비교가 되게 해요.

### 3. 몇 차례 반복해서 다듬기 (최소 2라운드)
- 라운드마다: 헤드리스 브라우저로 **스크린샷을 찍어 직접 보고**, 깨진 레이아웃·겹침·안 눌리는 버튼·어색한 문구를 고쳐요.
  - macOS 예: `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --hide-scrollbars --window-size=1400,1000 --virtual-time-budget=3000 --screenshot=<scratchpad>/round1.png file://<경로>`
  - 애니메이션·전환 효과는 테스트용 복사본에서 꺼야 스크린샷이 정확해요. 테스트용 파일은 스크래치패드에만 만들어요.
- 각 라운드에서 무엇을 고쳤는지 한두 줄로 기록해요.
- 라운드가 끝날 때마다 사용자에게 짧게 진행 상황을 알려요.

### 4. 직접 하나 고르고 이유 말하기
- **먼저 내가 하나를 고르고** 이유를 말해요. "다 장단점이 있어요"로 끝내지 않아요.
- 이유는 이 서비스의 목표·사용자·기존 화면과의 일관성·구현 난이도 기준으로 2~4줄.
- 나머지 안 중 아깝거나 섞어 쓸 만한 요소가 있으면 한 줄로 덧붙여요.
- 비교 파일을 사용자가 바로 볼 수 있게 열어줘요 (`open <파일>`).

### 5. 고른 안을 실제 코드에 구현 → 검증 → 기존 스타일 맞추기
- 고른 안을 **실제 서비스 파일**에 반영해요. 기존 코드의 변수명·주석 밀도·말투·디자인 토큰을 그대로 따라요.
- 검증:
  - 브라우저 콘솔 오류가 없는지 (`--enable-logging=stderr` 로 `Uncaught` 확인)
  - 핵심 상호작용을 테스트용 복사본에서 자동으로 눌러보고 결과 화면을 스크린샷으로 확인
  - 휴대폰 폭(390px)에서 가로 스크롤·겹침이 없는지
- 검증 결과는 사실대로 보고해요. 못 확인한 건 못 했다고 말해요.

### 6. 스크린샷을 첨부해서 PR 열기
- 최종 스크린샷(고른 안의 실제 반영 화면 + 비교 파일 전체 모습)을 `prototypes/screenshots/<기능-slug>/` 에 저장해요.
- **올리기는 반드시 `safe-push` 스킬로** 해요. (파일 확인 → 사용자 확인 → 저장·올리기)
- PR 본문에는: 기능 설명, 비교한 N개 안 요약, 고른 안과 이유, 검증 내용, 스크린샷(레포에 올린 이미지 경로를 마크다운 이미지로), 참고한 출처.
- `gh` 가 있으면 `gh pr create` 로 열고, 없으면 본문이 미리 채워진 PR 링크(`https://github.com/<owner>/<repo>/compare/<base>...<branch>?expand=1&title=...&body=...`)를 만들어 주고 "링크를 열고 초록 버튼만 누르면 돼요"라고 안내해요.

## 마무리 보고 (짧게)
- 비교 파일 경로, 고른 안과 이유, 실제로 바뀐 파일, 검증 결과, PR 링크
- 참고한 출처 링크

## 하지 말 것
- 변형 N개를 "서로 다른 방법"이라고 내놓기
- 동작하지 않는 그림 목업
- 사용자 확인 없이 올리기 (`safe-push` 생략)
- 비밀 값(API 키 등)을 preview나 코드에 넣기
